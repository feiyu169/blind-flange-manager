# ADR-003: 选择 JWT 作为认证方案

## 状态

接受

## 背景

项目需要选择用户认证方案。主要候选方案：
- JWT (JSON Web Token)
- Session + Cookie
- OAuth 2.0

项目需求：
1. 前后端分离
2. 移动端支持
3. 无状态认证
4. 安全性

## 决策

选择 **JWT** 作为认证方案。

## 理由

### JWT 优势

1. **无状态**
   - 服务器不需要存储会话信息
   - 适合分布式部署
   - 减少服务器内存占用

2. **前后端分离**
   - Token 可以存储在客户端
   - 适合 SPA 和移动端
   - 跨域请求友好

3. **自包含**
   - Token 中包含用户信息
   - 减少数据库查询
   - 适合微服务架构

4. **标准化**
   - RFC 7519 标准
   - 广泛支持
   - 工具链成熟

### JWT 劣势

1. **Token 吊销困难**
   - 无法主动使 Token 失效
   - 需要黑名单机制
   - 密码修改后需要特殊处理

2. **Token 大小**
   - Token 包含用户信息
   - 请求头较大
   - 需要压缩优化

3. **安全性**
   - Token 泄露风险
   - 需要 HTTPS
   - 需要定期轮换密钥

## 实现方案

### Token 结构

```json
{
  "sub": "1",
  "exp": 1715852820,
  "iat": 1715808820
}
```

### Token 吊销

1. **密码修改时吊销**
   - 记录密码修改时间
   - 验证 Token 签发时间
   - 拒绝旧 Token

2. **用户禁用时吊销**
   - 检查用户状态
   - 拒绝禁用用户的 Token

### 安全措施

1. **密钥管理**
   - 使用强密钥（256位）
   - 定期轮换密钥
   - 环境变量存储

2. **Token 过期**
   - 访问令牌：8小时
   - 刷新令牌：7天（待实现）

3. **HTTPS**
   - 强制使用 HTTPS
   - 防止 Token 窃取

## 后果

### 正面影响

- 前后端分离友好
- 无状态，易于扩展
- 移动端支持好

### 负面影响

- Token 吊销需要额外机制
- 需要处理 Token 刷新
- 安全性依赖密钥管理
