# ADR-004: 选择 Gateflow 工作流模式

## 状态

接受

## 背景

项目需要选择开发工作流模式。主要候选方案：
- 传统瀑布流
- 敏捷开发（Scrum/Kanban）
- Gateflow 工作流模式

项目需求：
1. 复杂项目管理
2. 代码质量保证
3. 风险追踪
4. 多 Agent 协作

## 决策

选择 **Gateflow 工作流模式**（源自 code-is-cheap 项目）。

## 理由

### Gateflow 优势

1. **Gate-based 推进**
   - 每个阶段有明确的门禁标准
   - 必须通过才能进入下一阶段
   - 保证代码质量

2. **风险追踪**
   - 每个实现/fix 报告必须列出 residual risks
   - 分类追踪风险状态
   - 避免风险遗漏

3. **多 Agent 协作**
   - 支持 controller-worker 模式
   - 明确角色职责
   - 支持并行任务

4. **文档驱动**
   - 必须有设计文档
   - 必须有实施计划
   - 必须有审查报告

### Gateflow 劣势

1. **流程复杂**
   - 阶段较多（7+个）
   - 文档要求高
   - 执行成本高

2. **不适合小项目**
   - 对于简单任务过于繁琐
   - 需要裁剪流程
   - 学习曲线较高

## 实现方案

### 工作流阶段

```
需求澄清 → 计划制定 → 计划审查 → 切片实施 → 代码审查 → 深度审查 → 优化迭代
```

### 门禁标准

1. **计划审查门禁**
   - 计划完整性
   - 技术可行性
   - 风险识别

2. **代码审查门禁**
   - 代码质量
   - 安全性
   - 测试覆盖

3. **深度审查门禁**
   - 架构合理性
   - 性能优化
   - 文档完整性

### 风险追踪

每个实现/fix 报告必须包含：
- 风险描述
- 风险分类
- 处理方式
- 负责人

## 后果

### 正面影响

- 代码质量高
- 风险可控
- 文档完整
- 可追溯性强

### 负面影响

- 开发周期长
- 文档工作量大
- 流程执行成本高

## 使用场景

### 适合使用 Gateflow

- 复杂项目（>5个模块）
- 架构敏感任务
- 需要严格质量控制
- 多人协作项目

### 不适合使用 Gateflow

- 简单任务（<3个文件）
- 原型开发
- 紧急修复
- 个人小项目
