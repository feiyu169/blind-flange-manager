# 第三方评估模板

## 概述

在 ready-to-create-PR 之后、创建 PR 之前，进行第三方资深专家评估。评估后进行至少三轮讨论，对 P0/P1 事项逐项讨论，直至达成一致。

## 评估流程

```
ready-to-create-PR
    ↓
【第三方评估】← 资深专家评估，30-60分钟
    ↓
第一轮：开发者回应评估问题
    ↓
第二轮：专家回应并提出建议
    ↓
第三轮：双方达成共识
    ↓
【逐项讨论】
    ↓
P0 事项逐项讨论（每项至少一轮，最多三轮）
    ↓
P1 事项逐项讨论（每项至少一轮，最多三轮）
    ↓
（如果未达成共识，继续讨论，最多五轮）
    ↓
提交评估报告
    ↓
创建 PR
```

## 评估边界条件

| 条件 | 规则 |
|------|------|
| 评估时机 | ready-to-create-PR 之后、创建 PR 之前 |
| 讨论目的 | 澄清事实，达成共识 |
| 讨论范围 | P0 和 P1 事项必须逐项讨论，P2 事项可以跳过 |
| 讨论顺序 | 先讨论 P0 事项，再讨论 P1 事项 |
| 讨论轮数 | 每项至少讨论一轮，最多三轮 |
| 讨论结果 | 每项必须达成一致意见，否则记录为"未达成一致" |

## 评估维度

### 1. 代码质量（权重：30%）

**检查指标**：
- ruff 错误数
- 类型注解完整度
- 代码复杂度
- 代码重复率

**评分标准**：
- 90-100%：优秀（ruff 错误 = 0，类型注解完整）
- 70-89%：良好（ruff 错误 < 5，类型注解基本完整）
- 50-69%：一般（ruff 错误 < 10，类型注解部分缺失）
- <50%：需要改进（ruff 错误 > 10，类型注解严重缺失）

### 2. 安全性（权重：30%）

**检查指标**：
- 安全扫描结果
- 认证完整性
- 密钥管理
- 依赖漏洞

**评分标准**：
- 90-100%：优秀（无高危漏洞，认证完整）
- 70-89%：良好（无高危漏洞，认证基本完整）
- 50-69%：一般（有中危漏洞，认证部分缺失）
- <50%：需要改进（有高危漏洞，认证严重缺失）

### 3. 文档完整性（权重：20%）

**检查指标**：
- ADR 数量
- API 文档覆盖率
- README 完整度
- 代码注释覆盖率

**评分标准**：
- 90-100%：优秀（ADR ≥ 4，API 文档完整，README 详细）
- 70-89%：良好（ADR ≥ 2，API 文档基本完整，README 基本详细）
- 50-69%：一般（ADR ≥ 1，API 文档部分缺失，README 简单）
- <50%：需要改进（无 ADR，API 文档严重缺失，README 不完整）

### 4. 测试覆盖（权重：20%）

**检查指标**：
- 测试覆盖率
- 测试通过率
- 边界测试
- 集成测试

**评分标准**：
- 90-100%：优秀（覆盖率 > 80%，通过率 100%）
- 70-89%：良好（覆盖率 > 70%，通过率 > 95%）
- 50-69%：一般（覆盖率 > 60%，通过率 > 90%）
- <50%：需要改进（覆盖率 < 60%，通过率 < 90%）

## 评估结果

| 结果 | 条件 | 处理方式 |
|------|------|----------|
| PASS | 无阻断问题 | 直接创建 PR |
| PASS_WITH_TODO | 有改进问题 | 创建 PR + 记录改进项 |
| FAIL | 有阻断问题 | 必须修复后重新评估 |

## 阻断条件

以下情况必须阻断，不能创建 PR：

1. **P0 安全问题**：
   - 硬编码密钥
   - 无认证方案
   - 无 HTTPS 支持

2. **P0 架构问题**：
   - 数据库选型错误
   - 中间件选型错误
   - 部署环境不明确

3. **测试覆盖率 < 50%**

## 不阻断条件

以下情况不阻断，记录为改进项：

1. **P1/P2 问题**
2. **文档不完整**
3. **代码规范问题**

## 讨论流程

### 第一轮：开发者回应评估问题

**目的**：澄清事实，提供上下文

**内容**：
- 回应评估中的问题
- 提供设计决策的理由
- 解释实现方式的选择

### 第二轮：专家回应并提出建议

**目的**：提供专业建议，指出改进方向

**内容**：
- 回应开发者的解释
- 提供专业建议
- 指出改进方向

### 第三轮：双方达成共识

**目的**：达成一致意见，确定最终决定

**内容**：
- 讨论分歧点
- 达成共识
- 确定最终决定

### 逐项讨论

**目的**：确保所有 P0/P1 事项都被讨论，达成共识

**流程**：
1. 先讨论 P0 事项（每项至少一轮，最多三轮）
2. 再讨论 P1 事项（每项至少一轮，最多三轮）
3. 如果未达成共识，继续讨论，最多五轮

**格式**：
```markdown
#### P0-1: [问题描述]
- 开发者观点：[观点]
- 专家观点：[观点]
- 最终决定：[达成一致/未达成一致]
- 讨论轮数：[轮数]
```

## 使用方式

### 1. 触发条件

在 ready-to-create-PR 之后、创建 PR 之前触发。

### 2. 执行方式

使用 delegate_task 派发评估任务：

```python
delegate_task(
    goal="作为第三方资深专家，评估以下项目的质量...",
    context="[项目信息 + 代码变更 + 测试结果]",
    toolsets=["terminal", "file"]
)
```

### 3. 讨论方式

使用 clarify 工具进行多轮讨论：

```python
# 第一轮：开发者回应
clarify(question="请回应评估中的问题")

# 第二轮：专家回应
clarify(question="请提供专业建议")

# 第三轮：达成共识
clarify(question="请确认最终决定")
```
